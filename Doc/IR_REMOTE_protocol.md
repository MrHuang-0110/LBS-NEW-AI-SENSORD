# 红外发射/接收传感器（IR_REMOTE）通信协议

> 面向主机侧（NEW-AI）接入开发。本文档自包含，无需读固件源码即可实现收发。
> 固件仓库：`LBS-NEW-AI-SENSORD`｜产品宏：`IR_REMOTE=1`｜Keil 工程：`Project/PY32_IR_REMOTE.uvprojx`

---

## 1. 概述

IR_REMOTE 是一对**收发共板**的红外模块：一块板子当**发射端**接主机，另一块同样的板子当**接收端**用电池供电、不接主机。两块板烧**同一份固件**，上电时由 PB2 引脚决定角色。

对主机来说，**只有一个设备**，即发射端：

| 项目 | 值 |
| --- | --- |
| ObjectID | **`0xA3`** |
| SourceID | **`0x97`**（本系列所有传感器相同） |
| 串口 | **115200 8N1**（设备侧 USART1，PA3=TX / PA4=RX） |
| 数据上报 | 握手后**每 10 ms** 一帧，index `0xED` |
| 控制命令 | `0xD1` 切换接收端颜色（4 态） |

发射端会把主机的颜色指令通过红外转发给接收端。

> **本产品硬件不含反向链路**：发射端板上只有红外 LED、**没有红外接收头**，接收端的电量无法回传。
> 因此上报的 `bat` 字段**恒为 `0xFF`（未知）**，该字节仅为将来硬件改版预留。

**主机不需要、也无法与接收端直接通信**——接收端不接主机、不初始化串口。

## 2. 帧格式

与 NEW-AI 系列其它传感器**完全一致**：

```text
[0x5A][ObjectID][SourceID][len][typeIndex][payload...][crc][0xA5]
  0     1          2        3      4          5..        n-2   n-1
```

- `0x5A` 帧头，`0xA5` 帧尾
- `ObjectID` 固定 `0xA3`（设备发出的帧）；主机下发的帧按惯例填 `0xA3`
- `SourceID` 固定 `0x97`
- `len` = payload 字节数（**本设备最大 32**，超出整帧丢弃并重新同步）
- `typeIndex` = 命令/上报类型
- `crc = (0x5A + ObjectID + SourceID + len + typeIndex + Σpayload) & 0xFF`，即**帧头到 payload 末尾的字节和取低 8 位**，不含 crc 和帧尾
- 总帧长 = `len + 7`

> 设备侧解析器**只校验**：帧头、`len ≤ 32`、CRC、帧尾。
> ObjectID / SourceID 两个字节**不校验**（只记录），因此主机按惯例填写即可。

## 3. 命令集（主机 → 设备）

| typeIndex | payload | 名称 | 行为 |
| --- | --- | --- | --- |
| `0x09` | ASCII `"Please Link"`（11 字节，必须完全一致） | 握手 | 回复 `"Play Aplication"`（index `0x09`），并**开始上报**。握手前设备不上报任何数据 |
| `0xD1` | 1 字节 `state` | 切换颜色 | `0=灭 1=红 2=绿 3=蓝`；同时点亮发射端自身 RGB，并向接收端连发 3 帧红外 |
| `0xEE` | 无（len=0） | 重启 | `NVIC_SystemReset()` |
| 其它 | — | — | **静默忽略** |

### 3.1 握手（`0x09`）

- payload 必须是 11 字节且逐字节等于 `"Please Link"`，否则忽略。
- **设备回复字符串故意拼错**：`"Play Aplication"`（`Application` 少一个 `p`）。
  这是本系列固件的历史约定，**主机必须按这个错误拼写逐字节匹配，不要"纠正"它**。
- 握手成功后连接状态**不会超时**（固件里没有链路超时逻辑）。主机重连时重发 `0x09` 即可再次收到应答；只有设备复位或收到 `0xEE` 才会回到未握手状态。

### 3.2 切换颜色（`0xD1`）

- payload **至少 1 字节有效**：`payload[0] = state`
- `state` 取值 `0/1/2/3`；**≥4 的值直接被忽略**（不改变状态、不发红外）
- 该命令是**命令态**语义：设备记录下来并在 `0xED` 上报中回显，**不代表接收端已收到或已执行**
- **重复下发相同 `state` 不会重复连发红外**：只有 `state` 发生变化才连发 3 帧；保持不变化时由发射端每秒的刷新连发维持。主机以 **10 Hz 反复重发当前状态是安全的**；若每个重复命令都触发一次连发，红外会变成接近 100% 占空比的连续发射，接收头 AGC 会失聪、接收端反而收不到（实测：0.1 s 重发不行，0.5 s 可以）

## 4. 数据上报（设备 → 主机）

| typeIndex | payload | 周期 |
| --- | --- | --- |
| `0xED` | 2 字节，见下 | 握手后每 **10 ms** 一帧 |

payload 是一个 **packed 结构体**：

```c
typedef struct __attribute__((packed)) {
    uint8_t state;   /* 0=灭 1=红 2=绿 3=蓝          */
    uint8_t bat;     /* 0..100 = 接收端电量百分比；0xFF = 未知 */
} ir_packet_t;       /* sizeof == 2 */
```

字段语义（**主机接入时最容易搞错的地方**）：

| 字段 | 语义 | 说明 |
| --- | --- | --- |
| `state` | **命令态**，不是回执 | 主机最后下发的有效颜色值。接收端没上电、超距、被遮挡时它**依然照常变化**。上电初值为 `0`（灭），不做持久化 |
| `bat` | **当前硬件恒为 `0xFF`（未知）** | 为将来硬件改版预留。原因：发射端板只有红外 LED、没有红外接收头，接收端电量无法回传。主机应始终按 `0xFF` 处理，并据此显示"未知"而不是 255% |

**本设备的上报包没有 `version` 字段**（与电机/颜色/灰度传感器不同），主机侧解析不要按带版本号的布局去偏移。

## 5. 示例帧（CRC 已实测校验）

主机 → 设备：

```text
握手请求         5A A3 97 0B 09 50 6C 65 61 73 65 20 4C 69 6E 6B B0 A5
0xD1 灭          5A A3 97 01 D1 00 66 A5
0xD1 红          5A A3 97 01 D1 01 67 A5
0xD1 绿          5A A3 97 01 D1 02 68 A5
0xD1 蓝          5A A3 97 01 D1 03 69 A5
0xEE 重启        5A A3 97 00 EE 82 A5
```

设备 → 主机：

```text
握手应答         5A A3 97 0F 09 50 6C 61 79 20 41 70 6C 69 63 61 74 69 6F 6E 66 A5
                                                        └── "Play Aplication" ──┘
上报 灭+电量未知  5A A3 97 02 ED 00 FF 82 A5
上报 红+电量50%   5A A3 97 02 ED 01 32 B6 A5
上报 蓝+电量100%  5A A3 97 02 ED 03 64 EA A5
```

对应 ASCII：

- `"Please Link"` = `50 6C 65 61 73 65 20 4C 69 6E 6B`
- `"Play Aplication"` = `50 6C 61 79 20 41 70 6C 69 63 61 74 69 6F 6E`

## 6. 时序与状态机

```text
主机                                设备(发射端)                    接收端
 │                                     │                             │
 │ ── 0x09 "Please Link" ────────────► │                             │
 │ ◄──── 0x09 "Play Aplication" ───── │                             │
 │                                     │                             │
 │ ── 0xD1 01 (红) ──────────────────► │ 本地RGB=红                  │
 │                                     │ ── 红外连发 3 帧 (0x5A) ──► │ RGB=红
 │                                     │        (无反向链路)          │ 电量只在本地
 │ ◄── 0xED {01, FF} 每10ms ───────── │                             │ PB0 低电闪烁
 │        ...                          │ ── 每1s刷新连发3帧 ───────► │ (重同步)
```

要点：

- **握手前零上报**。主机应以"连接后是否在 ~100 ms 内收到 `0xED`"作为在线判据。
- `0xED` 每 10 ms 一帧（约 100 Hz）。单帧 9 字节，115200 下带宽占用很低。
- 设备在**未握手时也照常每秒发红外刷新连发（3 帧）**，但颜色固定为 `0`（灭），所以接收端此时不亮灯属正常现象。
- 接收端**把最后一次有效的红/绿/蓝指令保持 5 秒**：重复同一颜色、切换不同颜色或发射端每秒的刷新连发都会重新计时；收到 `0xD1 00` 立即熄灭。即使某个刷新帧的命令字节被干扰损坏，只要帧头/地址仍是本设备的 `0x5A`，接收端仍视作“还在接收”并重新计时；两端**贴在一起**时 38 kHz 解调头会过载、帧根本解不出来，此时只要 PA1 上还检测到载波（解调输出拉低）也照样重新计时，避免近距离饱和导致提前熄灭。发射端停止、被遮挡或掉电（连线变安静）后，接收端才会在最后一次活动约 5 秒后自动熄灭。注意这是接收端本地的超时行为，主机侧 `0xED` 的 `state` 仍按命令态上报，不受影响。
- `bat` **恒为 `0xFF`**：发射端无红外接收头，反向链路（接收端回传电量）在当前硬件上不可能实现。接收端的电量只在本机 PB0 上体现（≤10% 时 2 Hz 闪烁）。

## 7. 主机端接入清单

1. **设备表**新增一项：`ObjectID = 0xA3`，名称如"红外发射/接收"，解析器复用现有多传感器框架。
2. **握手**：连接后发送 `0x09 "Please Link"`（**注意应答字符串的拼写**）。
3. **解析 `0xED`**：按 2 字节 packed 结构读 `state` / `bat`，**不要**按 4 字节 version 布局解析。
4. **下发颜色**：构造 `0xD1` + 1 字节 `state`。
5. **UI 映射**：
   - `state` → 灭 / 红 / 绿 / 蓝 四态选择器
   - `bat == 0xFF` → 显示"未知/未连接"；`0..10` → 低电量告警；`11..100` → 百分比显示
6. **可选**：提供"重启设备"按钮 → `0xEE`。

### 参考实现（伪代码）

```python
OBJ, SRC = 0xA3, 0x97

def build(payload: bytes, index: int) -> bytes:
    body = bytes([0x5A, OBJ, SRC, len(payload), index]) + payload
    return body + bytes([sum(body) & 0xFF, 0xA5])

LINK   = build(b"Please Link", 0x09)          # 握手
def color(state: int) -> bytes:               # 0..3
    return build(bytes([state]), 0xD1)
REBOOT = build(b"", 0xEE)

def parse(frame: bytes):
    """返回 (index, payload) 或 None"""
    if len(frame) < 7 or frame[0] != 0x5A or frame[-1] != 0xA5:
        return None
    if sum(frame[:-2]) & 0xFF != frame[-2]:
        return None
    n = frame[3]
    if n + 7 != len(frame):
        return None
    return frame[4], frame[5:5 + n]

def parse_upload(frame: bytes):
    """0xED -> (state, bat)"""
    r = parse(frame)
    if not r or r[0] != 0xED or len(r[1]) != 2:
        return None
    return r[1][0], r[1][1]
```

## 8. 注意事项与常见错误

| # | 事项 |
| --- | --- |
| 1 | 应答字符串 `"Play Aplication"` **故意拼错**，按错误拼写匹配，不要"修正" |
| 2 | `0xED` 的 `state` 是**命令态**，不是接收端回执。不能用它判断接收端是否真的变色 |
| 3 | `bat = 0xFF` 是"未知"哨兵值，不要按 255% 处理 |
| 4 | 上报包**没有 version 字段**，与其它传感器的解析布局不同 |
| 5 | 设备**不持久化**任何状态：复位后 `state=0`、`bat=0xFF`、需要重新握手 |
| 6 | `0xD1` 传入 ≥4 的值会被静默忽略（不会报错，也不会上报变化） |
| 7 | 主机只与**发射端**通信；接收端是电池供电的独立板子，没有 UART 链路 |
| 8 | 未握手时设备不上报任何数据，但每秒仍在发红外刷新连发（3 帧，颜色=灭） |
| 9 | 设备侧 `len` 上限为 32 字节，超长帧会被丢弃并重新同步 |
| 10 | 同一串口上可能有多个传感器（不同 ObjectID），按 `frame[1]` 过滤 `0xA3` |

## 9. 相关硬件参数（供联调参考）

| 项目 | 值 |
| --- | --- |
| MCU | PY32F002Bx5（24 KB Flash / 3 KB RAM，AC5） |
| 固件运行地址 | `0x08000000`（**无 bootloader**，独立运行） |
| 烧录 | UL2CM3 + `PY32F002Bxx_24.FLM` |
| 主机串口 | USART1，PA3=TX / PA4=RX，115200 8N1 |
| 角色判定 | 上电读 PB2：**高=发射端**（接主机），**低=接收端**（电池供电）。内部上拉，**悬空=发射端** |
| 红外载波 | **由 MCU 自己产生 38 kHz**：PA0 驱动裸红外 LED，每个 mark 是一串 38 kHz 脉冲（低=发射中）；PA1 接 38 kHz 一体化解调接收头（低=有载波） |
| 红外编码 | NEC 风格：9 ms 引导 + 4.5 ms 间隔 + 32 位（地址/反码/命令/反码），560 µs 位宽 |
| RGB | PA5/PA6/PA7，高电平亮 |
| 状态灯 | PB0，**低电平亮**：发射端=已握手 1 Hz 闪烁／未握手灭；接收端=常亮／电量 ≤10% 时 2 Hz 闪烁 |
| 电池 | 接收端 PB1，`ADC_CHANNEL_0`（PB1 = ADC_IN0），3×7 号电池，1/2 分压；线性 3.0 V=0% … 4.5 V=100% |
