# AGENTS.md

Workspace guide for ZCode agents. **Read [CLAUDE.md](CLAUDE.md) first** — it is the canonical, detailed project guide. This file is a short quick-reference; defer to CLAUDE.md for anything not covered here.

## What this repo is

Unified firmware for small sensor/actuator peripherals talking to a host over UART. **Seven independent single-target Keil µVision projects** (one per product) across three chip platforms. No Makefile/CMake, no test framework — verification is on hardware over UART.

| Project file (Keil) | Chip | Product macro | ObjectID |
| --- | --- | --- | --- |
| `Project/HK32_BIG_MOTOR.uvprojx` | HK32F030MF4P6 | `BIG_MOTOR=1` | 0xA1 |
| `Project/HK32_SMALL_MOTOR.uvprojx` | HK32F030MF4P6 | `SMALL_MOTOR=1` | 0xA6 |
| `Project/HK32_COLOR.uvprojx` | HK32F030MF4P6 | `COLOR=1` | 0xA2 |
| `Project/STM32_GRAY_V1.uvprojx` | STM32G030F6P6 | `GRAY_V1=1` | 0xA9 |
| `Project/STM32_GRAY_V2.uvprojx` | STM32G030K6T6 | `GRAY_V2=1` | 0xB0 |
| `Project/STM32_NFC.uvprojx` | STM32G030F6P6 | `NFC_G030F6=1` | 0xB2 |
| `Project/PY32_IR_REMOTE.uvprojx` | PY32F002Bx5 | `IR_REMOTE=1` | 0xA3 |

**Why single-target:** Keil µVision (V6.24, verified on official projects) merges ALL targets' files into the active target for ANY multi-target project — a multi-target `.uvprojx` is unusable in UV4 (GUI Rebuild and CLI `-b` both do it). Do NOT reintroduce a multi-target project; see the comment in the Boot_All repo's `tools/gen_boot_all_uvprojx.py` for the original finding.

## Directory map (platforms do not share a compilation unit)

- `Project/` — `senords.h`/`senords.c` (HK32 app layer + product macros), seven single-target Keil projects (`HK32_*.uvprojx`, `STM32_*.uvprojx`, `PY32_IR_REMOTE.uvprojx`) generated by `tools/gen_single_uvprojx.py` (templates = the generated projects themselves; only TargetName/Output/Define/IncludePath/Groups/fromelf are rewritten, the per-product AC5/AC6 compiler, memory layout and debugger are kept). The old multi-target `Project.uvprojx` was **removed** — never create a multi-target project here (UV4 multi-target merge bug).
- `Source/` — HK32F030M platform (vendor std-periph lib). `User/` = main.c + IRQ; `Handware/` = shared wire protocol, queue, USART, TIMER, PWM, IIC, ltr381xx. `Libraries/` = **upstream vendor CMSIS + peripheral lib — do not edit.**
- `G0/` — STM32G030 platform (STM32 HAL). `Core/` shared startup/system; `HAL/` vendor HAL+CMSIS (do not edit); `App/{gray_v1,gray_v2,nfc}/` each product's own `main.c` + peripherals + IRQ (isolated by target file groups).
- `PY32/` — PY32F002B platform (Puya HAL). `Core/` startup + system; `HAL/` vendor PY32F002B HAL + CMSIS (do not edit); `App/ir_remote/` the IR product — **one firmware for both roles**, PB2 sampled once at boot (HIGH = emitter, LOW = receiver).
- `Doc/` — empty Readme only.
- `tools/` — `gen_single_uvprojx.py` (regenerates the 7 single-target projects — **use this one**), `gen_uvprojx.py` (legacy multi-target generator — **do not use**, UV4 merge bug), `syntax_check.py` (GCC sanity check, all 7 products), `arm_ext.h` (stubs `__weak`/`__align` for gcc).

## Build / check / clean

- **Build:** open the product's project file in Keil µVision (e.g. `Project/HK32_BIG_MOTOR.uvprojx` or `Project/STM32_GRAY_V1.uvprojx`), then build (F7). Each file is single-target and carries its own product Define. Compiler per product: HK32×3 + GRAY_V2 use AC6 (`uAC6=1`), NFC uses AC5, GRAY_V1 uses AC6 — keep this (AC5 code is ~0x2ac bytes bigger and overflows the HK32 16 KB flash; HK32 must stay AC6; GRAY_V1 also needs AC6 to fit the 18 KB bootloader app region).
- **Flash:** HK32 via J-Link (`HK32F030MXX_16.FLM`); STM32G030 via ST-Link; PY32F002B via UL2CM3 (`PY32F002Bxx_24.FLM`). Each project's after-build runs fromelf `--bin` → `Project/Objects/<PRODUCT>/<PRODUCT>.bin` (APP image for the bootloader; HK32 app base `0x08002000`, G0 `0x08003800`).
- **Syntax sanity (no Keil needed):** `python tools/syntax_check.py` — runs after structural edits across all 7 product source sets (it derives the repo root from its own location and normalises `\` separators, so it runs on Windows and on Linux/WSL). `arm_ext.h` stubs ARM-isms so gcc can parse.
- **Clean intermediates:** `keilkill.bat` from repo root (keeps `*.opt`). Build artifacts under `Project/Objects/`, `Project/Listings/` are gitignored.

## Critical rules (easy to break)

- **Exactly one product macro must be `1`** — injected via the Keil target's Define, or set manually in `senords.h`. `senords.h` `#error`s otherwise. `USER_SourceID` is `0x97` for all products.
- **HK32 `tx_cache` is 32 bytes** → `SendCOMdataByte` payloads > ~25 bytes overflow. Keep packet structs packed and small.
- **Don't parse the wire protocol in ISRs.** RX → interrupt → 16×32B ring queue → main-loop `pull_data_from_queue()`. Never block in an ISR.
- **HK32 IWDG is enabled** (`IWDG_Prescaler_128`, reload 49), fed only in the main loop — a hung ISR resets the chip.
- New message types go in the existing `typeIndex` switch (or the per-product parse in `G0/App/*`); do **not** add a parallel parser.
- **PY32 `IR_REMOTE` is one firmware for two roles**: PB2 is read once at boot (HIGH = emitter, LOW = receiver). The receiver never initialises USART1 and never talks to the host. The emitter board has only an IR LED and **no IR receiver head**, so the reverse link is compiled out (`IR_REVERSE_LINK 0`): `bat` is always reported as `0xFF` and the receiver's battery is only shown locally on its PB0. The receiver holds the last valid red/green/blue frame for **5 s** (restarted by repeats, colour changes and the emitter's 1 s refresh burst of 3 frames, and also by frames whose command byte is damaged but whose forward address validates, and by any 38 kHz carrier seen on PA1 (overloaded demodulator at very short range)); command 0 turns the RGB off immediately and a silent emitter leaves it off after the timeout. On the emitter, re-sending the **same** `0xD1` state is deliberately a no-op for the IR burst (only a change re-bursts), so a host that repeats its state at 10 Hz cannot turn the link into a ~100 % duty IR stream that deafens the receiver's AGC.
- **PY32 has no bootloader**: `PY32_IR_REMOTE` links at `0x08000000` and does no VTOR relocation (unlike GRAY_V1/GRAY_V2 at `0x3800`).
- The IR envelope timings (9 ms/4.5 ms header, 560 µs bit marks) come from `tim.c`'s TIM14 1 µs counter — `HAL_GetTick()` is far too coarse. `ir_send_frame()` blocks ~68 ms per frame (worst case ~200 ms for a 3-frame burst).
- `G0/App/nfc/user/queue.c` and `Source/Handware/queue/queue.c` are near-identical per-platform ring queues — **do not merge across platforms.**
- `KT_MOTOR` variant + `KTH782xx/` and `SPI/` drivers were **removed** — do not reintroduce (kept as `#define KT_MOTOR 0` for legacy compat only).
- **GBK-encoded Chinese comments** are common in `Source/` and `G0/App/*` — preserve encoding; don't re-encode wholesale.
- HK32 `bool` is split two ways and must not be mixed: `Source/User/define.h` typedefs its own `bool`/`BOOL` as `volatile unsigned char` (legacy), but `Source/User/main.c`, `TIMER/timer.c`, and `Project/senords.c` use C99 `<stdbool.h>` for the `linkState`/`uploadState` flags. `uploadState` is **defined in `timer.c`** and `extern` in `main.c` — both must see the same stdbool `bool` or the extern type mismatches; any TU touching these flags needs `#include "stdbool.h"`, not `define.h`'s typedef.
- `Source/Handware/tftprintf/printf.c` is a tiny ported printf for output routing, not the toolchain printf.

## Wire protocol (shared on USART1 115200 8N1)

`[0x5A][ObjectID][SourceID][len][typeIndex][payload...][crc&0xFF][0xA5]`. Outbound via `SendCOMdata` (text) / `SendCOMdataByte` (binary). `0x09` "Please Link" handshake must complete before any upload (reply `"Play Aplication"`). G0 products each carry their own copy of the framing (GrayV1 inlines in usart.c; GrayV2 = `agreement_comx.c` `MultiUart_SendFrame`; NFC = `user/data_analysis.c`) — same framing, `USER_ObjectID` from `senords.h`. `IR_REMOTE` adds `0xD1 <state>` (set the receiver colour, 0=off 1=red 2=green 3=blue) and uploads `ir_packet_t{state, bat}` on `0xED`.

## Bootloader / vector-table notes (don't break these)

- HK32 `main()` relocates vector table to `FLASH_BASE | 0x2000` (bootloader @ 0x2000); device version read from `0x08001900`.
- GRAY_V1 and GRAY_V2 set `SCB->VTOR = FLASH_BASE | 0x3800` (bootloader @ 0x3800, apps linked 0x08003800); GRAY_V2 calibration cfg @ `0x08007800`, version @ `0x08007900` (Flash).
- G0 targets have **no IWDG**; VTOR relocation (0x3800) is done by GRAY_V1 and GRAY_V2, not by NFC (standalone @ flash base).
- PY32 `PY32_IR_REMOTE` is standalone at flash base (no bootloader, no VTOR change, no IWDG).
